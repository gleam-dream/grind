# Declare the settlement of abandoned jobs on the worker

<a id="adr-0021"></a>

## Decision

- A worker may declare a settlement with `worker.with_settlement`: a function of an open transaction and the abandoned job that returns ConfirmSuccess, ConfirmFailure, AuthorizeReplay or LeaveUncertain, or an error to ask for a later try. The abandoned job is an opaque `grind/abandoned` value read through accessors, with a closed cause (lease expired or timed out) and the count of replays already authorized; `testing.abandoned` builds one for a test.
- When Grind holds a job uncertain because an attempt ended without the handler's acknowledgement and the job is not replayed (lease expiry with no replay left or with cancellation pending, or a handler timeout under HoldUncertain), it writes a settlement mark naming that attempt. A handler timeout is acknowledged as an abandonment, a proposal kind of its own, so that the acknowledgement can write the mark; a handler's own Uncertain response writes none. The mark is written whether or not any worker declares a settlement.
- The settler of a queue consumer takes a due job of a registered worker version that declares a settlement in a committed statement that moves its due time later and counts the try. In a process of its own, the try then locks the job without waiting, decodes its input and runs the function in one Grind-owned transaction, under the application's search_path. It applies the decision through the existing resolution protocol, under a resolution identity in a prefix Grind reserves and attributed to the worker's settlement, and ends the mark in the same transaction. LeaveUncertain commits the application's writes and ends the mark. Every other outcome, including a decision the resolution protocol refuses and input the deployed codec cannot decode, is a failed try: it commits nothing and the job is due again later. Two decisions get a fixed meaning instead: ConfirmFailure on a worker without an error codec commits a business failure with no stored error, as the handler's own failure does, and AuthorizeReplay under a pending cancellation, which can never commit, ends the mark as declined without the function's writes.
- `admin.settle_due` runs the same takes and tries on demand for nodes whose consumers are polled by hand or not at all, and `admin.list` shows each job's settlement mark.
- Schema version 14 adds the mark, with its check `NOT VALID` and no new index so that nothing scans or rebuilds the job table under the lock the new columns take, and marks jobs already held uncertain by lease expiry, recognised as uncertain with no acknowledgement receipt for their retained attempt, so a settlement declared afterwards settles them too. Jobs a handler timeout held uncertain before version 14 carry a receipt like a handler's own Uncertain response and stay with an operator.
- This amends ADR-0013, which introduced borrowed resolution with no application-function protocol, background process or schema migration. Borrowed resolution stays; the settlement adds all three for this one case.
- Grind still never decides whether uncertain work happened. The application decides, in its own transaction.

## Rationale

- The first production consumer held an agent job uncertain after two node restarts and never reconciled it, because nothing told the application that the job needed a decision. The only signals were a best-effort quarantine observation and a list query an application has to remember to poll. Any application that declares an abandonment policy needs the same sweep, and the first consumer had to write one: a supervised process, paging, binding, a transaction and a resolution identity scheme.
- The worker already owns the abandonment policy, the codecs that decode the input and the error type a ConfirmFailure must encode. Declaring the settlement there keeps the decision next to the policy that creates the case.
- A durable mark, rather than process memory, makes the hand-over survive restarts: a job abandoned while no node ran is marked by the first quarantine scan and settled by the first settler that registers its worker. The mark names the abandoned attempt, so it has no effect once the job is resolved, claimed again or acknowledged; no other write has to clear it, and a node that predates the mark cannot make a stale one hand over the wrong uncertainty.
- Taking a job in its own committed statement before the function runs means a crash, a node death or a lost connection leaves the job due later rather than at once, so one failing job cannot be retaken ahead of every other. The try count reaches the function, so the application can stop trying with LeaveUncertain; Grind keeps trying with a delay that doubles from one lease to one hour, because a fix deployed later should still settle the job. A refused decision is retried for the same reason: the refusals the resolution protocol returns are a deployed function's mistakes, which a later deploy can correct, mixed with transient storage errors that the next try should simply repeat.
- One transaction carries the application's writes, the resolution and the ended mark. Whatever commits, commits together. A commit whose reply is lost is unknown; the next take selects only jobs still uncertain under the same mark, so it either finds the job settled or tries again.
- The original attempt cannot contradict the settlement: its acknowledgement requires a live lease, and the job was only marked after that lease expired or after Grind's own timeout acknowledgement.
- Every Grind storage call runs on a managed checkout bounded by the storage deadline (ADR-0008), and that checkout sets Grind's schema for its duration. The settlement keeps that bound rather than borrowing an application transaction, and hands the function the application's search_path saved by the checkout, set for the function's part of the transaction only. Grind sets its schema and timeouts again before its own statements and treats a transaction the function ended or replaced as a failed try.
- Each try runs in a process linked to the settler, which ends the try at the storage deadline, because the deadline closes the connection but cannot interrupt a function stuck outside the database. The settler sits under a supervisor of its own, a transient child of the consumer's supervisor, because that supervisor restarts every child together and a crashing settler must not stop claims and renewals; a supervisor that exhausts its restarts exits normally, which a transient child does not escalate.

## Alternatives

- **A declarative outcome on the abandonment policy, such as fail when replays are exhausted.** It needs no application function, but it cannot write the application's own rows, so the first consumer would keep its sweep. A settlement that returns ConfirmFailure and writes nothing expresses the same thing.
- **A reconciler registered on the queue or runtime that receives uncertain jobs.** The execution site is right, and the settler is that process. Declaring the function away from the worker splits the decision from the codecs and policy it depends on, and a renamed or re-versioned worker silently stops matching its reconciler.
- **Documenting the sweep and leaving the code unchanged.** That is the status quo that failed in production.
- **Running the function inside the claim-time quarantine statement.** It leaves no durable state for a retry, blocks every later expired row in the queue behind a failing function, and runs application code in the coordinator that also owns claims and capacity.
- **Remembering retries and declined jobs in process memory, without a migration.** A restart would ask again about a job the application already declined, and the declining transaction may have committed writes that the repeat duplicates.
- **Leaving a timed-out HoldUncertain attempt to lease expiry when a settlement is declared, so that one statement writes the mark.** Declaring a settlement would then change the abandonment policy's behaviour, delay the decision by a lease and lose the timeout evidence. Grind's timeout acknowledgement knows it records an abandonment and writes the mark itself.
- **Ending the mark after a fixed number of failed tries, or on a refused decision.** A job whose mark ended is as easy to miss as a never-settled one, and a refusal is often corrected by a later deploy. The function sees the try count and can decline after its own limit.
- **Borrowing an application transaction, as `admin.resolve_uncertain_in` does.** It would give the function the application's session directly, but the settlement's storage calls would then escape the storage deadline that bounds every other Grind storage call.
- **Refusing a ConfirmFailure without an error codec, at run time or when the worker is built.** A run-time refusal retries a decision no later try can change and recreates a quieter stuck job; a build-time refusal forbids the codec-less workers that only confirm success or decline. Committing the failure without a stored error matches what the same worker's handler commits.
- **Exposing the cause only as the description text.** Applications would branch on strings Grind writes for people. A closed cause states it once, in the type.
- **An open record for the abandoned job.** Every field added later would break applications that build one in a test.
- **Making a settlement mandatory for workers that replay.** A forgotten case would fail compilation, but every existing consumer would break. The absence of a settlement stays visible at run time through the uncertain listing and the quarantine observation.
- **Handing handler-reported uncertainty to the settlement too.** A handler that returns Uncertain has already decided that an operator must look; settling it automatically would change the meaning of that response.
- **Reusing `admin.Decision` as the function's result.** `grind/admin` depends on `grind`, which depends on `grind/worker`, so the worker cannot name it, and moving it would break every existing `admin.ConfirmSuccess` caller.

## Consequences

- Every consumer applies schema version 14 before running this Grind, including consumers that declare no settlement; Cigogne users add its mirror file. Without a declared settlement, abandoned jobs are marked and wait for an operator: no settler starts and no settlement query runs.
- A node on the previous Grind release that only checks the schema at start, or skips that check, runs on schema 14. One that migrates at start refuses to start on a newer schema, as for any migration. A node on the previous release writes no mark, so a job it holds uncertain during a rolling deploy waits for an operator; each settler marks such jobs of its queue when it starts, by the recognition schema 14 uses, so the next start of an upgraded node hands them over.
- The function runs while the job row is locked, in a transaction on the main pool bounded by the storage deadline. It must make only short database writes and must not end the transaction; an external call in it repeats with every try. On a runtime built from a database URL, the pool is Grind's alone, so the function sees Grind's schema and qualifies its own tables.
- An expired lease does not prove the abandoned handler stopped: a node cut off from the database may still run it until its own timeout. The function sees when the job was held uncertain and can return an error to wait; operators faced the same window before, at human pace.
- Operators see each job's mark in the listing and end it by resolving the job; whether they need a command to end or postpone a mark is an open ruling. Adding the mark to `admin.JobSummary` changes that public record, so code that builds one breaks; code that reads it by label does not.
- A function that returned a decision can run again: a try that fails after it returns, before COMMIT, commits none of its writes and is tried again. A settlement that needs a slow outside read submits a checker job on its own transaction with `grind.submit_in` and returns LeaveUncertain; the checker resolves the job once it has its evidence.
- Settlement needs the deployed typed worker. A job of a worker version no consumer registers stays due until one does; a queue no node consumes is never settled.

## Evidence

- The build adds PostgreSQL tests that drive expired leases by moving `lease_expires_at` to the database clock and stepping consumers manually, as the existing quarantine tests do. They are to cover a settlement that runs once, one for a job abandoned before any consumer started, atomic commit and rollback of application writes, a failing and a crashing function, a late acknowledgement, a declined and a refused decision, a timeout under HoldUncertain, and a worker without a settlement, a hanging function and a function that ends its transaction.
