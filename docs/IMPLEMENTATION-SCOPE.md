# Implementation scope

## Delivered in the current PostgreSQL slice

- Caller-defined worker inputs, outputs, and errors use ordinary versioned JSON
  codecs. Worker identity and codec metadata come from the definition; registry
  selection binds types before heterogeneous storage.
- PostgreSQL settings are validated before the package starts a connection pool,
  including a bounded uniqueness-lock wait (`unique_lock_wait`, default 5000ms,
  must be positive). Experimental schema version 11 is fresh-install-only:
  `migrate` creates five tables, the noncycling bigint attempt sequence, a
  partial index supporting uniqueness candidate lookups, and the sole version
  marker in one transaction. It accepts only that complete object set and
  marker; partial objects and older or future markers fail closed without
  repair. A schema installed at version 10 (the prior experimental marker) is
  rejected as `UnsupportedSchemaVersion(10)`; there is no migration path from
  v10 to v11, and a v10 database must be reinstalled from empty. Repeated
  migration leaves jobs, receipts, and sequence position unchanged. No upgrade
  path is promised for earlier experimental schemas. Existing version 11
  schemas receive relation-kind and marker checks, not exhaustive validation of
  manually altered columns or constraints; tampering may therefore surface at
  the operation that uses the changed object. See
  [docs/UNIQUENESS-CONTRACT.md](UNIQUENESS-CONTRACT.md) for the full schema v11
  change and its user impact.
- Grind owns the pool under a package supervisor, and the admission test closes
  and reopens the same pool name before reading persisted state. PGO may log a
  shutdown error when its asynchronous connection starter is blocked reloading
  type metadata during pool teardown; active-query draining and quiet shutdown
  remain unverified.
- Admission returns typed handles without running handlers. Handles retain the
  storage owner, queue, worker contract, and result codecs. Committed success and
  caller-codec-backed business failure can be read through typed outcomes. A
  process can rebuild a typed handle from a durable numeric ID and the worker
  definition after verifying the stored worker, codec, and storage route.
  Numeric IDs are scoped to the PostgreSQL storage owner, not globally unique.
- Absolute one-time scheduling accepts an opaque nonnegative `job.AvailableAt`.
  Due checks use PostgreSQL time. Automatic polling is the only wakeup
  mechanism. Grind has no LISTEN/NOTIFY channel at all — confirmed by
  source inspection alone (a test cannot prove that absence). Separately, a
  mutation-proven test
  (`postgres_automatic_consumer_wakes_for_database_deadline_test`,
  `docs/RECOVERY-EVIDENCE.md`) proves a scheduled job's claim genuinely
  waits for database time via polling: a pre-deadline poll tick is directly
  observed skipping the row before the deadline-crossing claim happens.
- The common worker path remains `perform(input) -> Result(output, error)`.
  Definition-bound queue handlers can return retry, snooze, discard,
  cancellation, or uncertainty proposals without changing direct
  `worker.invoke`; the queue invokes only one handler. Each job persists a
  positive `max_attempts` limit (default 20), separate from `delivery_count`.
  A returned business failure uses the definition's custom retry policy or a
  deterministic exponential default beginning at 15 seconds and capped at one
  day. A retryable failure commits `retryable`; exhaustion or policy refusal
  commits `business_failed` with `BudgetExhausted` or `RetryDeclined`, preserving
  a caller-typed error only when its explicit codec is configured. The policy
  callback sees typed business failures before erasure; worker death, invalid
  input, and runtime faults bypass it and follow conservative operational
  recovery. A snooze commits `scheduled`, increments `snooze_count`, and refunds
  the current attempt count while retaining the delivery count. Claim
  acquisition increments both attempt and delivery counts; an unstarted claim
  refunds only the attempt count. The fenced ACK transaction atomically records its disposition,
  retry scheduling or snooze refund, and compact receipt. PostgreSQL
  computes relative deadlines from
  `clock_timestamp()`. The checked relative-delay limit is
  9,007,199,254,740 ms, a conservative Grind precision bound for the
  millisecond-to-microsecond `double precision` conversion; it is separate from
  the one-day default backoff cap. Tests cover custom and default retry, typed
  exhaustion/refusal, snooze refunds after audited replay, database-time
  deadlines, receipt binding/rollback, the maximum delay ACK, and fresh-only
  schema v11 install/refusal behavior.
- A supervised OTP consumer runs each attempt in a `Temporary` worker child and
  monitors that exact process before activation. Its pure policy validates a
  positive polling interval, jobs-per-poll limit, lease duration, and local
  concurrency limit. Manual and automatic polling enforce configured capacity;
  capacity is per consumer, not global across consumers. Worker death releases
  local capacity without restarting the effect; default recovery later
  quarantines its expired claim. Stop pauses new claims, keeps renewing active
  leases, and waits for active work through the configured drain grace. If the
  grace expires, it reports the active count and leaves those rows executing
  for reconciliation. The separate bounded supervisor teardown can still
  return a timeout. The integration test verifies that automatic polling stays
  paused and the active lease advances during drain. A stopped batch reports
  earlier calls that returned committed acknowledgements; the failing call is
  excluded even when it committed an operational disposition. A deterministic
  manual consumer is available as a distinct stepping capability.
- Ownership claims have attempt IDs, epochs, owners, and database-time leases;
  acknowledgements fence on those fields and live expiry. Output/error codec
  mismatches are rejected before invocation and persisted as nonclaimable
  `contract_mismatch` rows, so an incompatible head job does not starve later
  compatible work. An expired executing attempt is quarantined to
  `uncertain`, at most one per poll, but only when some consumer actually
  polls that exact queue with that exact `(worker_id, worker_version)` pair
  currently registered — the quarantine scan's own SQL scopes its candidate
  row to the polling consumer's queue and registered identities, the same
  eligibility filter `claim_one` itself uses. After a worker version bump (or
  a queue with no consumer left polling it), an old row already `executing`
  under the retired identity is never matched by that filter and stays
  `executing` with an expired lease indefinitely; nothing else scans for it.
  An audited `AuthorizeReplay` resolution is the only path to a new delivery
  after an unknown effect; a pending cancellation request blocks that
  resolution until evidence supports a terminal decision.
- An uncertain attempt retains its claim metadata until an operator applies an
  audited resolution. The resolution ledger binds its ID to the job route,
  worker contract, decision, actor/details, typed payload codec version,
  canonical JSONB payload, and committed target state. Repeating the command
  returns its original target state even after later execution changes the job,
  including when two identical resolution commands genuinely overlap (the
  second, forced by a real row-lock wait to observe the first's commit,
  re-reads the resolution receipt instead of misreporting the row's
  post-commit state as "reconciliation not required" — a defect fixed and
  proven under a real forced overlap; see `docs/RECOVERY-EVIDENCE.md`,
  "Concurrent audited resolution").
  An acknowledged attempt writes the job transition and a compact command
  receipt in one transaction. The receipt records storage/command, route,
  worker, attempt, committed state/cause/time, and a 32-byte SHA-256 proposal
  fingerprint. The fingerprint hashes a fixed-order envelope using PostgreSQL's
  JSONB text representation with explicit SQL-null presence flags; JSON object
  key ordering is normalized, while numeric text variants may conservatively
  conflict. It does not store or decode a typed historical proposal.
  `reconcile_acknowledgement` returns committed receipt facts, while `outcome`
  returns the job's current typed result. On a transaction error Grind checks
  the receipt before returning `QueueAckUnknown` with the command ID and exact
  in-memory proposal.
  A real backend termination during `COMMIT` returns Unknown, leaves the row
  executing without a receipt, and does not trigger a blind worker rerun. A
  separate pair of tests reproduces a genuinely _successful_ commit whose
  reply is lost, by forcing that one ack transaction's own `synchronous_commit`
  to `on` against a disposable cluster with no real standby, then terminating
  the backend once it parks in PostgreSQL's `SyncRep` wait (after its WAL
  record is already flushed locally) — confirmed against PostgreSQL's own
  "already committed locally" log line, not merely inferred. One test proves
  the existing receipt-lookup reconciliation resolves this case with no
  rerun; the other proves that if the store is also unavailable at that
  moment, the caller sees `QueueAckUnknown` (not a crash) and the commit
  still reconciles once the store returns. See `docs/RECOVERY-EVIDENCE.md`
  for the full mechanism and honest limits (backend termination is not a
  network partition; it is unverified whether pog/pgo's query timeout bounds
  a COMMIT on a half-open socket, and no Grind-level ack deadline exists
  either way). If the process crashes after an external effect
  and before it can retain or commit the proposal, the typed proposal may be
  unrecoverable.
- `grind/observation` exposes Grind's first Sinal event descriptor,
  `[grind, job, acknowledged]` (`acknowledged()`), emitted from `grind/postgres`
  through its own `sinal/forwarder.Forwarder` — never a plain `sinal.emit` —
  so a slow or raising attached handler stalls only the forwarder, never the
  coordinator or a worker. `postgres.Settings` gains a validated, positive
  `observation_capacity` (default 1024; `postgres.observation_capacity`) and
  `Database` starts and owns the forwarder, nested under its own supervisor
  added to the root as a `Temporary` child: a handler that itself exits or
  is killed (not just raises) can take the forwarder down, and repeated
  crashes can exhaust that nested supervisor's own restart budget, but a
  `Temporary` child's termination is never restarted and never counts
  against the root supervisor's own budget, so this can never affect the
  PostgreSQL pool — in that degraded state, `forwarder.emit` reports
  `ForwarderUnavailable` (already discarded), so admission, claiming, and
  acknowledgement keep working with observations simply unavailable
  (`postgres_forwarder_crash_loop_does_not_stop_the_pool_test`,
  `docs/RECOVERY-EVIDENCE.md`). The event is emitted only once its commit is proven —
  either this call's own transaction reply (`confirmation: Replied`) or a
  later receipt read after a lost reply (`confirmation: Reconciled`) — never
  from inside a transaction callback, and never for a rolled-back, aborted,
  stale, or commit-unknown acknowledgement. `committed_state` always comes
  from the acknowledgement's own committed disposition, never the worker's
  proposal, so a concurrent cancellation overriding a proposed success is
  visible in the event exactly as it is in the row. Delivery is best-effort
  (may repeat as a `Reconciled` duplicate of an earlier `Replied` event, may
  be lost) and per-producer FIFO; overflow past `observation_capacity` is
  reported once per drain via `sinal/forwarder`'s own
  `[sinal, forwarder, dropped]`, never affecting job outcomes. Proven by a
  real PostgreSQL suite covering commit ordering (read from inside the
  attached handler, which runs in the forwarder process), a blocked handler
  not stalling a second job's lease renewal/completion under the same
  coordinator, absence on a rolled-back/aborted/stale/commit-unknown
  acknowledgement, exactly one `Reconciled` event after a real lost-reply
  commit (the same `SyncRep` harness as the acknowledgement path itself),
  `committed_state` overriding a `proposed` success or retry on
  cancel-while-running, `available_at_unix_ms` reflecting the committed
  (never proposed) state, both receipt-match sites that prove `Reconciled`
  (a sequential duplicate ack and a forced-concurrent one), capacity overflow
  reporting `dropped` with job outcomes unchanged, a raising handler leaving
  job outcomes unchanged, and a handler that repeatedly kills its own
  process never stopping the pool — each with named-mutation evidence
  (`docs/RECOVERY-EVIDENCE.md`, "Acknowledged observation" and "Round 1
  follow-up"). The
  external `consumer/` package attaches `sinal.observe` to
  `grind/observation.acknowledged()` using only public imports and decodes a
  real committed record, proving the descriptor is usable end to end from
  outside the package. Round 2 delivers the remaining seven descriptors on
  the same forwarder, each emitted only once its own commit is proven and
  never from inside a transaction callback: `[grind, job, admitted]` (a plain
  `submit`/`submit_at`, or a `submit_unique` `Inserted`/`Existing`/
  `Rescheduled` decision, with `submission_id` and `Replied`/`Reconciled`
  confirmation for the unique case); `[grind, job, claimed]` (the claim's own
  autocommitted `RETURNING`, with `attempt_id`/`epoch`/attempt
  number/`previous_state`); `[grind, job, quarantined]` (one event per row
  the claim-time quarantine scan's own `RETURNING` reports abandoned, with
  `cancellation_was_requested`); `[grind, job, resolved]` (an audited
  resolution, `Replied` for `ResolutionApplied`, `Reconciled` for
  `ResolutionAlreadyApplied`); `[grind, job, cancellation]`
  (`CancelledBeforeRun`/`CancellationRequested` only — the read-only outcomes
  never emit, and `CancellationRequested` can repeat for an idempotent
  re-request); `[grind, job, released]` (`release_unstarted_claim` refunding
  an attempt whose worker child never started); and
  `[grind, job, contract_mismatch]` (a claimed attempt parked in the
  terminal, nonclaimable `contract_mismatch` state, not returned to
  `queued`, for a registered worker's codec no longer matching what was
  persisted at admission). Public `reconcile_unique` follows
  `reconcile_acknowledgement`'s
  round 1 precedent and never emits, even when it recovers a genuinely
  committed outcome recorded through `submit_unique` returning
  `CommitUnknown` — meaning `submit_unique` itself never emitted anything
  for that commit either (proven against the same "committed, reply lost,
  pool closed" scenario the equivalent `submit_unique` recovery test uses).
  This is a real, accepted gap in delivery, not a double-reporting
  safeguard: that admission can end up with no `admitted` observation at
  all, ever, even though the row and receipt are both fully correct — see
  README.md's "best-effort" bullet. Every new
  metadata type shares the same `JobRef`/`AttemptRef` codecs rather than
  redeclaring per event. A dedicated ordering test proves a coordinator's
  `claimed` event for one attempt always arrives before that attempt's
  `acknowledged` event (same producer, same forwarder, per-producer FIFO).
  Each descriptor has at least one emission test, one no-emission test using
  the same "next observation on this channel is a known sentinel" technique
  round 1 established, and a named-mutation proof — see
  `docs/RECOVERY-EVIDENCE.md`, "Round 2 observations". The external
  `consumer/` package additionally attaches to
  `grind/observation.claimed()` using only public imports.
- The external `consumer/` package uses only public Grind modules for two
  differently typed workers, tagged application errors, a configured queue, and
  typed committed outcomes. Its local synthetic effect has an application-owned
  deduplication key, exercised by two independently admitted jobs (no
  preseeding); this demonstrates caller-side idempotency only. It also
  exercises, through public imports alone: a definition-bound retry policy
  reaching a second delivery after a real delay; cooperative cancellation of
  a genuinely running attempt, committing `Cancelled` without undoing the
  handler's own already-performed effect; and a worker crash immediately
  after its effect surfacing as conservative `Uncertain` recovery, resolved
  through a rebound handle with `ConfirmSuccess` (no rerun) and
  `AuthorizeReplay` (a rerun whose repeated effect call is absorbed by the
  application's own idempotent table). See `docs/RECOVERY-EVIDENCE.md`
  (Increment 5) for mechanism and mutation evidence.
- `oracle/` runs pinned Oban OSS `v2.24.1` against a separate disposable database.
  Success, first retryable failure, and snooze state/accounting are differentially
  observed. Exhaustion state and backoff timing intentionally differ; the ledger
  records the tested normalization and the limits of each comparison.

| Uniqueness                                 | `submit_unique`/`reconcile_unique` (`docs/UNIQUENESS-CONTRACT.md`) implement conservative typed key equality (PostgreSQL `jsonb::text` SHA-256, exact equality not containment), queue scope, an occupancy period, the four named eligibility groups, a bounded advisory-lock wait, and compact receipts. Proven: sequential (non-concurrent) admission and identity; queue scope (`WithinQueue`/`AcrossQueues`); the full state-eligibility matrix across all 11 persisted states and all four `States` groups, plus a live transition through a real consumer; period-boundary timing at the database clock for both `UniqueTimestamp` origins, `while_retained()`, and the shared predicate at an exact microsecond instant; and `SubmissionId` receipt idempotency (replay after a period elapses, a changed-input conflict, replay returning the originally observed state, and a changed output codec version conflicting on replay); concurrent admission under a real, `pg_stat_activity`-verified, barrier-forced overlap of three simultaneous same-key submissions (one `Inserted`, two `Existing` against that same job id, one row), its mixed-scope variant (`WithinQueue` racing `AcrossQueues` on the same key), and the receipt lookup's real invariant — it must run after the domain lock and before this transaction's own write, proven both by a live in-flight scenario and by two mutations that move it to the two positions that are observably wrong (before the lock; after the insert), with a third, more literal reordering ("before candidate selection") shown to be unobservable on its own and documented as such; and lock contention (`AdmissionContended`) against both a real held domain lock and a real held candidate row lock, including that the bounded lock wait's transaction-local scope (`is_local: true`) does not leak into a later statement on the same reused pooled connection once that transaction commits (proven by mutation; a merely-contended, rolled-back attempt cannot distinguish this on its own). Every other transaction in `src/grind` was audited for the same class of hidden dependency (`docs/RECOVERY-EVIDENCE.md`, "Isolation-level pinning"): the acknowledgement and audited-resolution paths share it (fixed by the same pool-level pin); claim/quarantine/renew/migrate do not (single-statement implicit transactions or no wait at all). The four public admission-result types (`Admission`, `Conflict`, `SubmitError`, `PendingSubmission`) live in `grind/unique` alongside the policy types; `grind/internal/unique_admission` returns them directly, with no parallel mirror types or translator functions. `RescheduleScheduledTo` moves `available_at` only when a conflict is genuinely `scheduled` (re-checked under its own row lock), proven against every other conflicting state and against a live race with a real claim (the claim's row lock forces the reschedule's own candidate read to observe the row's fresh post-claim state via PostgreSQL's `EvalPlanQual`, not the stale value it started waiting behind), and against a rescheduled row's genuine claimability once due. Uncertain-commit reconciliation is proven against a real forced fault in four distinct shapes — an aborted commit, a genuinely committed admission (plain and reschedule alike) whose reply is lost, and the same loss with the store also unavailable. An independent review of the last shape found a genuine correctness bug (not a classification difference): `run`'s follow-up receipt lookup, needed after a mid-transaction connection loss, could itself fail to reach a now-closed store, and the unfixed code returned that lookup's own failure (`AdmissionFailed`) as if it were the admission's outcome, silently discarding the `PendingSubmission` a caller would need to ever learn a zombie transaction later committed. Fixed in two parts, both proven by red-before-fix and by mutation (`docs/RECOVERY-EVIDENCE.md`, Increment 11): a failed receipt lookup now reports `CommitUnknown` (mirroring the acknowledgement path's own `Ok(None) | Error(_) -> QueueAckUnknown`), and a new FFI wrapper (`transaction_or_checkout_failure`) distinguishes a checkout failure — the pool could not hand out a connection at all, so `BEGIN`never ran, knowably not committed, still`AdmissionFailed`with no`PendingSubmission`— from a mid-transaction loss, so the two are no longer conflated. Only a pool closed *before*`submit_unique`ever sends anything gives`AdmissionFailed`; a pool closed while a commit is genuinely parked now correctly gives a reconcilable `CommitUnknown`. The different-key/same-`SubmissionId` receipt-table race remains untested (`docs/UNIQUENESS-CONTRACT.md`). Broader field replacement (only `available_at`on`scheduled`rows is supported), arbitrary caller-supplied states, cross-worker uniqueness, bulk uniqueness, and backend-specific policies remain retained.
