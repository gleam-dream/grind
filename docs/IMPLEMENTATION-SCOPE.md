# Implementation scope

## Delivered in the current PostgreSQL slice

- Caller-defined worker inputs, outputs, and errors use ordinary versioned JSON
  codecs. Worker identity and codec metadata come from the definition; registry
  selection binds types before heterogeneous storage.
- PostgreSQL settings are validated before the package starts a connection pool,
  including a bounded uniqueness-lock wait (`unique_lock_wait`, default 2000ms,
  must be positive) and a deadline (`statement_deadline`, default 4000ms,
  enforced by Grind's own bounded checkout in `grind_postgres_ffi.erl` — a
  `pgo:checkout/2` with `timeout` set to `infinity` and one absolute
  `deadline` shared across candidate checkouts, invoking the storage operation
  at most once. The configured duration is attached to the pool by name via
  `persistent_term` owned by the supervised pool deadline process, including
  startup rollback and shutdown;
  vanilla `pog`/`pgo` from Hex expose no public API for this, so Grind depends
  on a tightly pinned version of both and matches pog's private `Connection`
  shape directly. The version ranges limit upgrade scope without guaranteeing
  private API stability; `pog_connection_pool_shape_test` checks the pog pool
  tuple, while startup/cache and reconnect regressions cover other private
  contracts)
  and migration deadline (`migration_deadline`, default
  30000ms), both validated positive; `unique_lock_wait` must also clear the
  checkout deadline by at least 1000ms (`UniqueLockWaitTooCloseToDeadline`
  otherwise). Once checked out, the deadline bounds storage work — inline SQL,
  Squirrel-generated calls, and a whole transaction including its own
  `BEGIN`/`COMMIT` — against a half-open or otherwise unresponsive connection.
  Initial connection/reconnection and waiting for an unavailable pool are not
  unconditionally bounded by that deadline;
  see `docs/RELEASE-READINESS.md` ("Acknowledgement deadline") and
  `docs/RECOVERY-EVIDENCE.md` for the mutation-proven mechanism and its
  fault-proxy evidence. `queue.start` rejects a lease
  that is too short relative to that deadline
  (`queue.LeaseTooShortForDeadline`) before starting any process. `migrate` is
  a real, forward-only, versioned migration runner
  (`grind/internal/migrations.migrations()`, currently two released
  versions, 11 and 12): each version's statements — including its own
  `grind_schema_migrations` marker insert — run inside one transaction, under
  a transaction-scoped advisory lock (`pg_advisory_xact_lock`, keyed by a
  fixed Grind string and the current schema, held only until that step's own
  transaction ends) that serialises concurrent migrators across processes,
  re-reading and skipping an already-applied step after the lock is acquired,
  and re-reading once more after running the step's own statements to
  confirm the schema now genuinely reports that step's version before
  committing. Each step's own transaction also sets a constant,
  transaction-local `lock_timeout` (2000ms) right after that advisory lock,
  so a statement that cannot acquire whatever lock it needs (an
  `ALTER`/`CREATE INDEX` against a large, actively used table) fails fast
  with `MigrationLockUnavailable(version)` instead of blocking for up to the
  full `migration_deadline_ms`. A step whose own statements fail rolls back
  cleanly and reports `MigrationStepFailed(version, error)` (or
  `MigrationLockUnavailable(version)` for the `55P03` case specifically);
  earlier committed steps and marker rows are unaffected, and a corrected
  re-run resumes from there. A step that may or may not have committed
  reports `MigrationCommitUnknown(version)`
  — a checkout failure before `BEGIN` ever ran, `BEGIN` itself failing or
  losing its reply, or a failed `ROLLBACK` after a statement error — and
  re-running `migrate` is always safe regardless of which one occurred.
  `read_schema_generation` fails closed before touching anything:
  an absent marker table with any `grind_`-prefixed object present, a marker
  that is not the exact contiguous range from the baseline (11) to its own
  maximum, a maximum above the highest version this build knows
  (`UnsupportedSchemaVersion`), a legacy pre-baseline marker such as the prior
  experimental v10 (also `UnsupportedSchemaVersion`), or a physical shape
  that does not _exactly_ match a known version's own declared set of
  `grind_`-prefixed relations (a stray one fails closed exactly like a
  missing one) plus any required key columns, all report
  `IncompatibleSchema`/`UnsupportedSchemaVersion` without modifying the
  schema; that version-vs-baseline check runs before any physical shape
  check, so a schema tagged with a foreign or future marker is rejected
  correctly even alongside unrelated foreign objects or a broken shape at an
  earlier, otherwise-valid version. There is still no migration path from
  the pre-migration-mechanism v10 experimental schema; a v10 database must
  be reinstalled from empty. Every migration file is also published in
  cigogne's own file format under `priv/migrations/` (with
  `priv/cigogne.toml`), each one's own first `up` statement the identical
  advisory-lock statement `migrate` itself runs so a cigogne-driven apply
  serialises against a concurrent `postgres.migrate` caller too, purely so
  an importing application can apply Grind's schema through cigogne
  (`cigogne.include_lib`) instead of through `postgres.migrate` — pick one
  owner per database, never both. Grind itself never reads those files at
  runtime, and a no-database conformance test
  (`grind_migrations_conformance_test`) proves they stay byte-for-byte in
  lockstep with `migrations()` using cigogne's own parser (via
  `config.get("grind")`, exercising `priv/cigogne.toml` itself), and that
  every released file (all but the newest) has a matching pinned sha256. See
  [docs/UNIQUENESS-CONTRACT.md](UNIQUENESS-CONTRACT.md) for the
  full schema v11 change and its user impact, and
  [docs/RECOVERY-EVIDENCE.md](RECOVERY-EVIDENCE.md), "Migration mechanism",
  for the mutation-proven evidence.
- `grind_v12` adds `grind_jobs.finished_at` (non-null iff `state` is one of
  the six terminal states, enforced by `grind_jobs_finished_at_check`,
  backfilled from existing rows) plus the retention-scan indexes
  (`grind_jobs_finished_idx`, `grind_unique_submissions_job_idx`,
  `grind_job_resolutions_job_idx`) and the claim/quarantine hot-path partial
  indexes (`grind_jobs_claim_idx`, `grind_jobs_quarantine_idx`). Unlike
  every prior version, its own statements do real, table-size-proportional
  work under one `ACCESS EXCLUSIVE` lock rather than only creating new,
  empty objects — see [README.md](../README.md), "Migrations", for the
  measured cost at scale, why `lock_timeout` does not bound it, and why it
  requires a stop-the-world deploy (old code writing a terminal state
  against the new schema fails `23514`; new code writing `finished_at`
  against the old one hits an undefined column).
- `postgres.prune_finished(database, older_than_ms:, limit:)` deletes
  finished-and-old-enough rows (scoped to the caller's own schema,
  oldest `finished_at` first, `FOR UPDATE SKIP LOCKED`); each deleted job's
  own acknowledgement/uniqueness/resolution receipts cascade with it via
  `grind_v12`'s own `ON DELETE CASCADE` foreign keys, not a second explicit
  delete this function also issues. `grind/pruner` is a supervised
  background process calling it on a timer with Oban-shaped defaults
  (`interval_ms` 30000, `limit` 10000, `max_age_ms` 60000, one call per
  tick, never draining a backlog within one), no leader election at all
  (`FOR UPDATE SKIP LOCKED` already makes concurrent callers safe), and a
  `[grind, prune, failed]` observation on a failed tick;
  `pruner.supervised(database, policy)` embeds it into an application's own
  supervision tree instead of the separate one `pruner.start` creates. No
  minimum retention floor beyond both arguments being positive. A
  `submit_unique` `KeepExisting` candidate is locked `FOR KEY SHARE`
  (previously unlocked), backstopped by the same `ON DELETE CASCADE`
  foreign keys for the one narrower race a row lock alone cannot close; and
  `attempt.claim_registered_job`/`postgres.cancel_lock`/`lease`'s own
  quarantine-scan candidate lock/`postgres.apply_uncertain_resolution`'s own
  row lock all use `FOR NO KEY UPDATE` (not `FOR UPDATE`) so none of them
  spuriously contends with that `FOR KEY SHARE` for an unrelated reason.
  `v12`'s own `ADD CONSTRAINT ... FOREIGN KEY` statements are each preceded
  by a `DELETE ... WHERE NOT EXISTS` cleaning up any already-orphaned
  receipt a long-running `v11` database could have accumulated, so the
  `ADD CONSTRAINT` itself (which validates every existing row) cannot fail
  `23503` on such a database; the schema compatibility check
  (`postgres.read_schema_generation`) also now requires all three foreign
  keys to exist (`migrations.Migration.foreign_keys`, checked against
  `pg_constraint` independently of `v12_shape`'s own relation check), so a
  database missing one fails closed. See [README.md](../README.md),
  "Retention", and [docs/UNIQUENESS-CONTRACT.md](UNIQUENESS-CONTRACT.md) for
  the full contract, and [docs/RECOVERY-EVIDENCE.md](RECOVERY-EVIDENCE.md),
  Increment 23, Increment 24, and Increment 25, for the mutation-proven
  evidence (Increment 25 also measures the cascade itself: ~66ms for a
  10,000-job/30,000-receipt batch, about 1.7% of the default
  `statement_deadline_ms`).
- Grind owns the pool under a package supervisor. Cooperative close rejects
  new Grind storage calls and waits for the owned pool, its internal children,
  and admitted calls to finish or die before purging the pool's caches.
  Public close can return `StopTimedOut` after six seconds while cleanup
  continues without killing application callers; the lifecycle owner retains
  its registration and deadline throughout that drain. Direct use of the
  internal raw pog connection must be drained by its caller, and forcibly
  killing the lifecycle owner is outside this cleanup guarantee. Quiet
  shutdown logging is not guaranteed.
- Admission returns typed handles without running handlers. Handles retain the
  queue, worker contract, and result codecs. Committed success and
  caller-codec-backed business failure can be read through typed outcomes. A
  process can rebuild a typed handle from a durable numeric ID and the worker
  definition after verifying the stored worker, codec, and queue route.
  Numeric IDs are scoped to the PostgreSQL schema (one Grind installation
  per schema — see README, "Isolation"), not globally unique.
- Absolute one-time scheduling accepts an opaque nonnegative `job.AvailableAt`.
  Due checks use PostgreSQL time. Automatic polling is the only wakeup
  mechanism. Grind has no LISTEN/NOTIFY channel at all — confirmed by
  source inspection alone (a test cannot prove that absence). Separately, a
  mutation-proven test
  (`postgres_automatic_consumer_wakes_for_database_deadline_test`,
  `docs/RECOVERY-EVIDENCE.md`) proves a scheduled job's claim genuinely
  waits for database time via polling: a pre-deadline poll tick is directly
  observed skipping the row before the deadline-crossing claim happens.
- The common worker path remains `perform(input) -> Result(output, error)`.
  Definition-bound queue handlers can return retry, snooze, discard,
  cancellation, or uncertainty proposals without changing direct
  `worker.invoke`; the queue invokes only one handler. Each job persists a
  positive `max_attempts` limit (default 20), separate from `delivery_count`.
  A returned business failure uses the definition's custom retry policy or a
  deterministic exponential default beginning at 15 seconds and capped at one
  day. A retryable failure commits `retryable`; exhaustion or policy refusal
  commits `business_failed` with `BudgetExhausted` or `RetryDeclined`, preserving
  a caller-typed error only when its explicit codec is configured. The policy
  callback sees typed business failures before erasure; worker death, invalid
  input, and runtime faults bypass it and follow conservative operational
  recovery. A snooze commits `scheduled`, increments `snooze_count`, and refunds
  the current attempt count while retaining the delivery count. Claim
  acquisition increments both attempt and delivery counts; an unstarted claim
  refunds only the attempt count. The fenced ACK transaction atomically records its disposition,
  retry scheduling or snooze refund, and compact receipt. PostgreSQL
  computes relative deadlines from
  `clock_timestamp()`. The checked relative-delay limit is
  9,007,199,254,740 ms, a conservative Grind precision bound for the
  millisecond-to-microsecond `double precision` conversion; it is separate from
  the one-day default backoff cap. Tests cover custom and default retry, typed
  exhaustion/refusal, snooze refunds after audited replay, database-time
  deadlines, receipt binding/rollback, the maximum delay ACK, and fresh-only
  schema v11 install/refusal behavior.
- A supervised OTP consumer runs each attempt in a `Temporary` worker child and
  monitors that exact process before activation. Its pure policy validates a
  positive polling interval, jobs-per-poll limit, lease duration, and local
  concurrency limit. Manual and automatic polling enforce configured capacity;
  capacity is per consumer, not global across consumers. Worker death releases
  local capacity without restarting the effect; default recovery later
  quarantines its expired claim. Stop pauses new claims, keeps renewing active
  leases, and waits for active work through the configured drain grace. If the
  grace expires, it reports the active count and leaves those rows executing
  for reconciliation. The separate bounded supervisor teardown can still
  return a timeout. The integration test verifies that automatic polling stays
  paused and the active lease advances during drain. A stopped batch reports
  earlier calls that returned committed acknowledgements; the failing call is
  excluded even when it committed an operational disposition. A deterministic
  manual consumer is available as a distinct stepping capability.
- Ownership claims have attempt IDs, epochs, owners, and database-time leases;
  acknowledgements fence on those fields and live expiry. Output/error codec
  mismatches are rejected before invocation and persisted as nonclaimable
  `contract_mismatch` rows, so an incompatible head job does not starve later
  compatible work. An expired executing attempt is quarantined to
  `uncertain`, at most one per poll, by every consumer polling that exact
  queue — scoped only by queue, not by any registered
  worker id/version (approved contract decision, 2026-09-25, "Old-version
  executing rows"; `docs/RELEASE-READINESS.md`). Quarantining never decodes
  or runs code, so a consumer's own per-poll scan covers an abandoned
  attempt left by a worker version that consumer no longer registers — after
  a worker-version bump, the old version's still-`executing` row is
  quarantined by the new consumer's own next poll, not left behind
  indefinitely. A separate public `postgres.quarantine_expired(database,
limit:)` sweeps expired executing rows across every queue in a storage
  owner, for a queue no consumer polls at all; `limit` is validated positive
  before touching storage. An audited `AuthorizeReplay` resolution is the
  only path to a new delivery after an unknown effect; a pending
  cancellation request blocks that resolution until evidence supports a
  terminal decision.
- An uncertain attempt retains its claim metadata until an operator applies an
  audited resolution. The resolution ledger binds its ID to the job route,
  worker contract, decision, actor/details, typed payload codec version,
  canonical JSONB payload, and committed target state. Repeating the command
  returns its original target state even after later execution changes the job,
  including when two identical resolution commands genuinely overlap (the
  second, forced by a real row-lock wait to observe the first's commit,
  re-reads the resolution receipt instead of misreporting the row's
  post-commit state as "reconciliation not required" — a defect fixed and
  proven under a real forced overlap; see `docs/RECOVERY-EVIDENCE.md`,
  "Concurrent audited resolution").
  An acknowledged attempt writes the job transition and a compact command
  receipt in one transaction. The receipt records storage/command, route,
  worker, attempt, committed state/cause/time, and a 32-byte SHA-256 proposal
  fingerprint. The fingerprint hashes a fixed-order envelope using PostgreSQL's
  JSONB text representation with explicit SQL-null presence flags; JSON object
  key ordering is normalized, while numeric text variants may conservatively
  conflict. It does not store or decode a typed historical proposal.
  `reconcile_acknowledgement` returns committed receipt facts, while `outcome`
  returns the job's current typed result. On a transaction error Grind checks
  the receipt before returning `QueueAckUnknown` with the command ID and exact
  in-memory proposal.
  A real backend termination during `COMMIT` returns Unknown, leaves the row
  executing without a receipt, and does not trigger a blind worker rerun. A
  separate pair of tests reproduces a genuinely _successful_ commit whose
  reply is lost, by forcing that one ack transaction's own `synchronous_commit`
  to `on` against a disposable cluster with no real standby, then terminating
  the backend once it parks in PostgreSQL's `SyncRep` wait (after its WAL
  record is already flushed locally) — confirmed against PostgreSQL's own
  "already committed locally" log line, not merely inferred. One test proves
  the existing receipt-lookup reconciliation resolves this case with no
  rerun; the other proves that if the store is also unavailable at that
  moment, the caller sees `QueueAckUnknown` (not a crash) and the commit
  still reconciles once the store returns. See `docs/RECOVERY-EVIDENCE.md`
  for the full mechanism and honest limits (backend termination is not a
  network partition; a real TCP fault proxy now proves a half-open socket
  during a `COMMIT`/`BEGIN`/renewal statement is bounded by Grind's own
  checkout deadline, `postgres.with_statement_deadline`, default 4000ms — see
  "Acknowledgement deadline" below and `docs/RECOVERY-EVIDENCE.md`). If the
  process crashes after an external effect
  and before it can retain or commit the proposal, the typed proposal may be
  unrecoverable.
- `grind/observation` exposes Grind's first Sinal event descriptor,
  `[grind, job, acknowledged]` (`acknowledged()`), emitted from `grind/postgres`
  through its own `sinal/forwarder.Forwarder` — never a plain `sinal.emit` —
  so a slow or raising attached handler stalls only the forwarder, never the
  coordinator or a worker. `postgres.Settings` gains a validated, positive
  `observation_capacity` (default 1024; `postgres.with_observation_capacity`) and
  `Database` starts and owns the forwarder, nested under its own supervisor
  added to the root as a `Temporary` child: a handler that itself exits or
  is killed (not just raises) can take the forwarder down, and repeated
  crashes can exhaust that nested supervisor's own restart budget, but a
  `Temporary` child's termination is never restarted and never counts
  against the root supervisor's own budget, so this can never affect the
  PostgreSQL pool — in that degraded state, `forwarder.emit` reports
  `ForwarderUnavailable` (already discarded), so admission, claiming, and
  acknowledgement keep working with observations simply unavailable
  (`postgres_forwarder_crash_loop_does_not_stop_the_pool_test`,
  `docs/RECOVERY-EVIDENCE.md`). The event is emitted only once its commit is proven —
  either this call's own transaction reply (`confirmation: Replied`) or a
  later receipt read after a lost reply (`confirmation: Reconciled`) — never
  from inside a transaction callback, and never for a rolled-back, aborted,
  stale, or commit-unknown acknowledgement. `committed_state` always comes
  from the acknowledgement's own committed disposition, never the worker's
  proposal, so a concurrent cancellation overriding a proposed success is
  visible in the event exactly as it is in the row. Delivery is best-effort
  (may repeat as a `Reconciled` duplicate of an earlier `Replied` event, may
  be lost) and per-producer FIFO; overflow past `observation_capacity` is
  reported once per drain via `sinal/forwarder`'s own
  `[sinal, forwarder, dropped]`, never affecting job outcomes. Proven by a
  real PostgreSQL suite covering commit ordering (read from inside the
  attached handler, which runs in the forwarder process), a blocked handler
  not stalling a second job's lease renewal/completion under the same
  coordinator, absence on a rolled-back/aborted/stale/commit-unknown
  acknowledgement, exactly one `Reconciled` event after a real lost-reply
  commit (the same `SyncRep` harness as the acknowledgement path itself),
  `committed_state` overriding a `proposed` success or retry on
  cancel-while-running, `available_at_unix_ms` reflecting the committed
  (never proposed) state, both receipt-match sites that prove `Reconciled`
  (a sequential duplicate ack and a forced-concurrent one), capacity overflow
  reporting `dropped` with job outcomes unchanged, a raising handler leaving
  job outcomes unchanged, and a handler that repeatedly kills its own
  process never stopping the pool — each with named-mutation evidence
  (`docs/RECOVERY-EVIDENCE.md`, "Acknowledged observation" and "Round 1
  follow-up"). The
  external `consumer/` package attaches `sinal.observe` to
  `grind/observation.acknowledged()` using only public imports and decodes a
  real committed record, proving the descriptor is usable end to end from
  outside the package. The remaining seven descriptors are delivered on
  the same forwarder, each emitted only once its own commit is proven and
  never from inside a transaction callback: `[grind, job, admitted]` (a plain
  `submit`/`submit_at`, a `submit_with_id` commit, or a `submit_unique`
  `Inserted`/`Existing`/`Rescheduled` decision, with `submission_id` and
  `Replied`/`Reconciled` confirmation for both the `submit_with_id` and
  `submit_unique` cases); `[grind, job, claimed]` (the claim's own
  autocommitted `RETURNING`, with `attempt_id`/`epoch`/attempt
  number/`previous_state`); `[grind, job, quarantined]` (one event per row a
  quarantine scan's own `RETURNING` reports abandoned — either a consumer's
  per-queue claim-time scan or the public `quarantine_expired` sweep — with
  `cancellation_was_requested`); `[grind, job, resolved]` (an audited
  resolution, `Replied` for `ResolutionApplied`, `Reconciled` for
  `ResolutionAlreadyApplied`); `[grind, job, cancellation_decided]`
  (`CancellationDecidedBeforeRun`/`CancellationDecidedWhileRunning` only — the
  read-only outcomes never emit, and `CancellationDecidedWhileRunning` can repeat for an idempotent
  re-request); `[grind, job, released]` (`attempt.release_unstarted` refunding
  an attempt whose worker child never started); and
  `[grind, job, contract_mismatch_recorded]` (a claimed attempt parked in the
  terminal, nonclaimable `contract_mismatch` state, not returned to
  `queued`, for a registered worker's codec no longer matching what was
  persisted at admission). Public `reconcile_unique` follows the same
  precedent as `reconcile_acknowledgement` and never emits, even when it recovers a genuinely
  committed outcome recorded through `submit_unique` returning
  `CommitUnknown` — meaning `submit_unique` itself never emitted anything
  for that commit either (proven against the same "committed, reply lost,
  pool closed" scenario the equivalent `submit_unique` recovery test uses).
  This is a real, accepted gap in delivery, not a double-reporting
  safeguard: that admission can end up with no `admitted` observation at
  all, ever, even though the row and receipt are both fully correct — see
  README.md's "best-effort" bullet. Every new
  metadata type shares the same `JobRef`/`AttemptRef` codecs rather than
  redeclaring per event. A dedicated test observes `claimed` before
  `acknowledged` for the same attempt in its scenario. The coordinator emits
  the claim and the attempt process emits the acknowledgement; Sinal's
  per-producer FIFO contract does not guarantee order across those producers.
  Each descriptor has at least one emission test, one no-emission test using
  the same "next observation on this channel is a known sentinel" technique,
  and a named-mutation proof — see
  `docs/RECOVERY-EVIDENCE.md`, "Round 2 observations". The external
  `consumer/` package additionally attaches to
  `grind/observation.claimed()` using only public imports.
- The external `consumer/` package uses only public Grind modules for two
  differently typed workers, tagged application errors, a configured queue, and
  typed committed outcomes. Its local synthetic effect has an application-owned
  deduplication key, exercised by two independently admitted jobs (no
  preseeding); this demonstrates caller-side idempotency only. It also
  exercises, through public imports alone: a definition-bound retry policy
  reaching a second delivery after a real delay; cooperative cancellation of
  a genuinely running attempt, committing `Cancelled` without undoing the
  handler's own already-performed effect; and a worker crash immediately
  after its effect surfacing as conservative `Uncertain` recovery, resolved
  through a rebound handle with `ConfirmSuccess` (no rerun) and
  `AuthorizeReplay` (a rerun whose repeated effect call is absorbed by the
  application's own idempotent table). See `docs/RECOVERY-EVIDENCE.md`
  (Increment 5) for mechanism and mutation evidence.
- `oracle/` runs pinned Oban OSS `v2.24.1` against a separate disposable database.
  Success, first retryable failure, and snooze state/accounting are differentially
  observed. Exhaustion state and backoff timing intentionally differ; the ledger
  records the tested normalization and the limits of each comparison.

| Uniqueness                                 | `submit_unique`/`reconcile_unique` (`docs/UNIQUENESS-CONTRACT.md`) implement conservative typed key equality (PostgreSQL `jsonb::text` SHA-256, exact equality not containment), queue scope, an occupancy period, the four named eligibility groups, a bounded advisory-lock wait, and compact receipts. Proven: sequential (non-concurrent) admission and identity; queue scope (`WithinQueue`/`AcrossQueues`); the full state-eligibility matrix across all 11 persisted states and all four `States` groups, plus a live transition through a real consumer; period-boundary timing at the database clock for both `UniqueTimestamp` origins, `while_retained()`, and the shared predicate at an exact microsecond instant; and `SubmissionId` receipt idempotency (replay after a period elapses, a changed-input conflict, replay returning the originally observed state, and a changed output codec version conflicting on replay). Concurrent admission is proven under a real, `pg_stat_activity`-verified, barrier-forced overlap of three simultaneous same-key submissions (one `Inserted`, two `Existing` against that same job id, one row), its mixed-scope variant (`WithinQueue` racing `AcrossQueues`), the receipt lookup's real ordering invariant (after the domain lock, before this transaction's own write — proven live and by mutation against both wrong positions), and lock contention (`AdmissionContended`) against both a held domain lock and a held candidate row lock, including that the bounded lock wait's transaction-local scope does not leak into a later statement on the same reused pooled connection (proven by mutation). Every pooled connection pins `default_transaction_isolation` to `read committed` (`postgres.validate`), proven necessary by mutation against a database configured with `repeatable read`; the admission transaction also pins it in-transaction as defense in depth. See `docs/RECOVERY-EVIDENCE.md`, "Isolation-level pinning", for the audit across every other Grind transaction (acknowledgement/audited-resolution share the pool-level pin; claim/quarantine/renew/migrate need none). The four public admission-result types (`Admission`, `Conflict`, `SubmitError`, `PendingSubmission`) live in `grind/unique` alongside the policy types, with no parallel mirror types. `RescheduleScheduledTo` moves `available_at` only when a conflict is genuinely `scheduled` (re-checked under its own row lock, including against a live race with a real claim via PostgreSQL's `EvalPlanQual`) and against a rescheduled row's genuine claimability once due. Uncertain-commit reconciliation is proven against a real forced fault in four shapes — an aborted commit, a genuinely committed admission (plain and reschedule) whose reply is lost, and the same loss with the store also unavailable. An independent review of the last shape found and fixed a genuine correctness bug in `run`'s follow-up receipt lookup, which could silently discard a `PendingSubmission` a caller needed to recover a zombie commit; see `docs/RECOVERY-EVIDENCE.md`, Increment 11, for the full red-before-fix and mutation-proven narrative. The different-key/same-`SubmissionId` receipt-table race remains untested (`docs/UNIQUENESS-CONTRACT.md`). Broader field replacement (only `available_at` on `scheduled` rows is supported), arbitrary caller-supplied states, cross-worker uniqueness, bulk uniqueness, and backend-specific policies remain retained. Admission uniqueness will not imply exactly-once execution. **Backlog**: `postgres.gleam`'s other `transaction_safely` callers (acknowledgement, audited resolution) still conservatively report their own "unknown" outcome for a checkout failure too, the same way `submit_unique` did before this fix — safe, only less precise. `unique.selected` projected keys are proven isolated by key name and by codec version independently of the projected value, never colliding with a `full_input()` key over the identical input, and compared by the same exact-equality (not containment) semantics already proven for full-input keys — proven by mutation (dropping the key name falsely collapses two differently-named selected keys onto one). The full admission flow — admit, detect an existing conflict, rebind it with `bind_handle`, replay a `SubmissionId`, and an `AcrossQueues`/`RescheduleScheduledTo` reschedule across queues — is also proven reachable and correct entirely through `consumer/`'s public imports, each proven by mutation (`docs/RECOVERY-EVIDENCE.md`, Increments 12-13). |
